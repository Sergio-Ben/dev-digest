## Codebase Patterns

- **2026-06-18** — `POST /skills/import` must be registered BEFORE `GET /skills/:id` in Fastify routes, otherwise Fastify matches the literal segment `import` as a UUID param and returns 422. Fixed by registering the static path first. Evidence: `server/src/modules/skills/routes.ts:60`.
- **2026-06-18** — Skills wiring in reviews: `run-executor.ts` fetches `agentsRepo.linkedSkills(agent.id)`, filters to `.skill.enabled`, and passes the bodies as `{ skills: skillBodies }` to `reviewPullRequest()`. `assemblePrompt` in reviewer-core renders `## Skills / rules` automatically when the array is non-empty — no reviewer-core changes needed. Evidence: `server/src/modules/reviews/run-executor.ts`.

- **2026-06-14** — Shared contracts (`@devdigest/shared`) are vendored as TWO hand-maintained copies — `server/src/vendor/shared/` and `client/src/vendor/shared/` — resolved by tsconfig path alias, NOT auto-synced. Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts`.
- **2026-07-28** — `GET /repos/:id/pulls` now also rolls up a per-severity FINDINGS breakdown (`PrMeta.findings`), superseding the in-code comment that said it was intentionally left off the list. Same on-read shape as score/cost: one `findings ⋈ reviews` join scoped by `workspace_id` + `inArray(prId)`, then JS grouping through the previously-dead `rollupSeverities` in `pulls/status.ts`. It counts findings from EVERY review of the PR (not just the latest), which is what makes it agree with the PR-detail severity chips — narrowing it to the latest review would silently desync the two surfaces. Evidence: `server/src/modules/pulls/routes.ts`, `server/src/modules/pulls/status.ts:23-31`.
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-06-17** — PR-list `GET /repos/:id/pulls` returns the latest batch's FINDINGS as full `Finding[]` records (not counts) under `PrMeta.findings`, mapped via `reviews/helpers.ts#findingRowToDto`; the client derives severity chips AND renders a hover popover from that one array (no second fetch, perfect chip↔popover consistency). The "latest review batch" here is a SEPARATE window from the cost block: cost windows over `agent_runs.ranAt`, findings windows over `reviews.createdAt` (both 120s). A pre-existing `rollupSeverities` helper in `modules/pulls/status.ts` (lowercase keys) was built for a counts-only variant — currently unused by the route. Evidence: `server/src/modules/pulls/routes.ts`.

- **2026-08-07** — Smart Diff (`modules/smart-diff/`) classifies file role by DIRECTORY over BASENAME: `dist/index.ts` must be `boilerplate`, not `wiring`, even though `index.ts` alone matches the wiring-filename list — check boilerplate dir segments before any basename rule. Also, a bare `config.ts` (no prefix) needed to count as wiring alongside `app.config.ts`/`next.config.mjs`, so the wiring regex uses an OPTIONAL prefix: `/^(.*\.)?config\.(ts|js|mjs|cjs|json)$/i`, not the more obvious `/^.+\.config\....$/i` which would miss the bare form. Evidence: `server/src/modules/smart-diff/classifier.ts`, `server/src/modules/smart-diff/constants.ts`.
- **2026-08-08** — `SmartDiffFile.finding_lines: number[]` is a COUNT/anchor list and deliberately not deduped, so it cannot identify a finding — the UI could scroll to a flagged line but never route to that finding's card. Fixed by adding `findings: {id, line}[]` alongside it, both projected from ONE sorted list in the service (`sorted.map(x => x.line)` / `sorted`) so the two arrays agree index-for-index; sorting them independently is how they'd silently drift. Evidence: `server/src/modules/smart-diff/service.ts:79-95`, `server/src/vendor/shared/contracts/brief.ts:84-105`.
- **2026-08-07** — `t.findings` has no `workspaceId` column of its own — it's only reachable/scoped by joining `t.reviews` (which does have `workspaceId`) via `reviewId`. Any per-workspace findings query needs that join (or, if you already resolved the specific `reviewId` under a workspace-scoped review lookup, a plain `eq(findings.reviewId, ...)` is safe without re-joining). Evidence: `server/src/db/schema/reviews.ts`, `server/src/modules/smart-diff/service.ts`.

- **2026-08-18** — `BriefService.composeAndPersist` had a dedicated `## Linked issue` prompt section (`brief/prompt.ts`) and a matching `issue` param on `composeBrief` (`brief/composer.ts`) that were fully implemented and unit-tested, but the service never populated `issue` — it only threaded `parseReferences`/`resolveReferences` output into `references` (folded generically into `## Referenced plans/specs`), so the dedicated section never fired in production. Fixed by mirroring `intent/service.ts:138-164`'s pattern inline in `composeAndPersist`, right after `parsedRefs`/`references` are computed: find the first `parsedRefs` entry with `kind === 'github'`, best-effort `github.getIssue(...)` (falling back to `github.getPullRequest(...)` on 404), catch-and-skip on any failure. Lesson: a port/prompt section existing and being unit-tested does NOT guarantee the orchestrating service actually wires it — check the service's actual call site, not just the leaf modules, when verifying an AC end-to-end. Evidence: `server/src/modules/brief/service.ts` (composeAndPersist), `server/src/modules/brief/prompt.ts:254-260`, `server/src/modules/intent/service.ts:138-164`.
- **2026-08-18** — `BriefService.compose` (`modules/brief/service.ts`) deliberately reorders the task-listed steps: it derives the cache-validity state key (headSha + changed paths + intent + provider/model — no blast, no diff) and checks `BriefRepository.getEnvelope` BEFORE loading the diff, calling `BlastService.getForPr(..., { summary: true })`, or resolving references — not in the naive numeric order those steps were originally described in. This is required, not stylistic: `getForPr({ summary: true })` costs one LLM call, so running it unconditionally on every request would silently break "a cache hit issues zero model calls" and the "cache hit is a single row read" latency promise. The expensive path (diff/blast/references/`composeBrief`/persist) only runs on a confirmed cache miss (or `force`), and that whole path is wrapped in a MODULE-LEVEL (not instance-level) single-flight keyed by `prId` — an instance-level map would not dedupe concurrent requests handled by two different `new BriefService(container)` instances, which is exactly how each request is constructed (mirrors `IntentService`). Evidence: `server/src/modules/brief/service.ts:9-20,90-194`.

## Tool & Library Notes

- **2026-08-08** — `GET /pulls/:id/smart-diff` declares only a `params` schema, and the client's `useSmartDiff` calls `api.get<SmartDiff>()` (a bare cast, no parse). So the Zod contract is compile-time only on this path: a `.default([])` on a new response field NEVER executes at runtime, and a React-Query cache entry written before the field existed still reaches components as `undefined`. Add the response schema, or write the consumer defensively (`file.findings ?? []`) — don't trust the default. Evidence: `server/src/modules/smart-diff/routes.ts:26-28`, `client/src/lib/hooks/smart-diff.ts`.
- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`.
- **2026-08-18** — Passing a Zod schema with a `.default(...)` field (e.g. `BriefRisk.endpoint_refs`) as the `schema` in `LLMProvider.completeStructured<T>({ schema: z.ZodType<T>, ... })` fails to typecheck even when `T` is explicitly supplied: `z.ZodType<T>` defaults its `Input` generic param to `T` too, but a schema with `.default()` has `Input !== Output` (the field is optional on input, required on output), so TS flags the object literal as non-assignable. Fixed with a narrow `schema: BriefSchema as unknown as z.ZodType<T>` cast — safe because only the Output side matters at the call site and `completeStructured` never re-serializes against `Input`. Evidence: `server/src/modules/brief/composer.ts`.

## Recurring Errors & Fixes

- **2026-06-14** — Adding a required field to a Zod contract (`RunStats.cost_usd`) breaks the inline fixture in `server/test/contracts.test.ts` (RunTrace parse). Update the `stats: {…}` fixture in the same change. Evidence: `server/test/contracts.test.ts:160`.
- **2026-08-18** — `server/src/db/migrations/meta/_journal.json` is missing entries for several committed `.sql` files (`0009_fantastic_rogue`, `0010_solid_baron_zemo`, `0011_far_stryfe`, `0012_concerned_blockbuster`, `0013_daffy_loa` — likely from divergent branches merged without renumbering; note also duplicate numeric prefixes, e.g. two different `0009_*`/`0010_*` files). `runMigrations()` reads only the journal, so those files are silently never applied — EVERY `*.it.test.ts` using `test/helpers/pg.ts#startPg()` fails at `buildApp`/`seed` time with `PostgresError: column "cost_usd" of relation "agent_runs" does not exist` (confirmed pre-existing on `reviews.it.test.ts`, unrelated to any one module's change). This is NOT fixable by hand-appending journal entries — some of the un-journaled files also collide (e.g. both `0009_fantastic_rogue` and `0012_concerned_blockbuster` `ADD COLUMN "created_at"` to `conventions`), so it needs real triage (dedupe/renumber the migration set), not a mechanical journal patch. Local diagnostic-only workaround (do not commit): point `startPg()` at `npx drizzle-kit push --force` (applies `db/schema.ts` directly, bypassing the SQL chain) instead of `runMigrations()` — confirmed this unblocks `*.it.test.ts` and is what verified `brief-service.it.test.ts`'s 9 cases end-to-end. Evidence: `server/src/db/migrations/meta/_journal.json`, `server/test/helpers/pg.ts`.
- **2026-08-18** — Refinement to the `drizzle-kit push --force` workaround above: a fresh `pgvector/pgvector:pg16` Testcontainer does NOT have the `vector` extension enabled yet — migration `0000_init.sql` creates it via `CREATE EXTENSION IF NOT EXISTS vector`, but `drizzle-kit push` only diffs `db/schema.ts` (which references the `vector` column type, not the extension statement) and fails with `PostgresError: type "vector" does not exist`. Run `CREATE EXTENSION IF NOT EXISTS vector` against the container (via a throwaway `createDb(url).db.execute(sql\`...\`)`) *before* invoking `drizzle-kit push --force`. Re-confirmed this unblocks `test/brief-service.it.test.ts` (all 11 cases) and `test/brief-repository.it.test.ts` (2 cases) end-to-end. Evidence: `server/test/helpers/pg.ts`, `server/src/db/migrations/0000_init.sql`.
