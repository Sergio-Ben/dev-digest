## What Doesn't Work

- **2026-08-27** — T7 (dashboard/compare): `EvalsRepository.getBatch(batchId)` has a genuine SQL bug, not just the documented workspace-scoping gap — its query `.groupBy(t.evalRuns.batchId)` groups by ONE column but `batchAggregateQuery()`'s shared SELECT also projects `agentId: t.evalCases.ownerId` (ungrouped, unaggregated), so Postgres throws `column "eval_cases.owner_id" must appear in the GROUP BY clause or be used in an aggregate function` on every real call — 500, not a silent wrong answer. This went undetected because nothing called `getBatch` against a live DB before T7's `compareBatches` did (T4 wrote it, T7 was its first real consumer). Fix applied WITHOUT touching `repository.ts` (out of T7's owned paths): `compareBatches` resolves both batch ids via `listBatches(agentId)` (correctly grouped by `(ownerId, batchId)`) + a `Map` lookup instead of calling `getBatch` at all — which also satisfies AC-40 for free (a batch id absent from that agent-scoped list is simply not found). `repository.ts#getBatch` itself still needs `.groupBy(t.evalCases.ownerId, t.evalRuns.batchId)` to actually work for any other caller. Evidence: `server/src/modules/evals/repository.ts` (`getBatch`, `batchAggregateQuery`), `server/src/modules/evals/dashboard.service.ts` (`compareBatches`).
- **2026-08-27** — T7: `EvalBatchAggregateRow.ranAt` is declared `Date` but at runtime is a STRING — postgres.js only auto-parses timestamps for direct column selects, not for a `max(ran_at)` SQL aggregate expression (same "declared type vs. runtime type" class as the already-documented NUMERIC/BIGINT aggregate coercion below, but `toBatchAggregate()` only wraps `recall/precision/citationAccuracy/tracesPassed/tracesTotal/costUsd` in `Number(...)` — `ranAt` is passed through unconverted). Calling `.toISOString()`/`.getTime()` on it throws `row.ranAt.toISOString is not a function`. `dashboard.service.ts` (T7) works around this LOCALLY (not editing `repository.ts`) with a `withDateRanAt()` helper applied to every row the moment it leaves the repository. Any other new consumer of `listBatches`/`getBatch`/`latestBatchPerAgent` needs the same guard until `toBatchAggregate` itself coerces `ranAt: new Date(row.ranAt)`. Evidence: `server/src/modules/evals/repository.ts` (`toBatchAggregate`), `server/src/modules/evals/dashboard.service.ts` (`withDateRanAt`).
- **2026-08-27** — `isConfigChange()` (`modules/agents/helpers.ts`) does NOT deep-compare `output_schema` — any patch that explicitly passes `outputSchema` (even a value identical to the current row's) is treated as a config change and unconditionally bumps the agent's version (`patch.outputSchema !== undefined` is the whole check). Any caller that wants a truly idempotent `update()` call (e.g. `AgentsService.promoteToVersion`, T17) must omit `output_schema` from the patch when `JSON.stringify(new) === JSON.stringify(current ?? null)`, rather than always forwarding it — otherwise every call bumps the version even when nothing actually changed. Confirmed via a throwaway Testcontainers script: promoting the agent's own current version bumped v4→v5 until this guard was added. Evidence: `server/src/modules/agents/helpers.ts:85` (`isConfigChange`), `server/src/modules/agents/service.ts` (`promoteToVersion`).

Adding a field means editing both in lock-step; the only diffs between copies are comments. Evidence: `server/src/vendor/shared/contracts/trace.ts`, `platform.ts`.
- **2026-06-14** — PR-list per-PR aggregates (score, cost) are computed ON READ in `GET /repos/:id/pulls` via one `inArray` query + JS grouping, never denormalized onto `pull_requests`. "Latest review batch" cost has no batch id in the schema — approximated by summing `agent_runs.cost_usd` within a 120s window of the PR's newest priced run. Evidence: `server/src/modules/pulls/routes.ts`.
- **2026-07-28** — `GET /repos/:id/pulls` now also rolls up a per-severity FINDINGS breakdown (`PrMeta.findings`), superseding the in-code comment that said it was intentionally left off the list. Same on-read shape as score/cost: one `findings ⋈ reviews` join scoped by `workspace_id` + `inArray(prId)`, then JS grouping through the previously-dead `rollupSeverities` in `pulls/status.ts`. It counts findings from EVERY review of the PR (not just the latest), which is what makes it agree with the PR-detail severity chips — narrowing it to the latest review would silently desync the two surfaces. Evidence: `server/src/modules/pulls/routes.ts`, `server/src/modules/pulls/status.ts:23-31`.
- **2026-06-14** — `completeAgentRun`'s `values` shape is declared in TWO places that must match: the repo fn (`repository/run.repo.ts`) AND the interface wrapper (`repository.ts:151`). Adding a field (e.g. `costUsd`) needs both or typecheck fails.
- **2026-06-17** — PR-list `GET /repos/:id/pulls` returns the latest batch's FINDINGS as full `Finding[]` records (not counts) under `PrMeta.findings`, mapped via `reviews/helpers.ts#findingRowToDto`; the client derives severity chips AND renders a hover popover from that one array (no second fetch, perfect chip↔popover consistency). The "latest review batch" here is a SEPARATE window from the cost block: cost windows over `agent_runs.ranAt`, findings windows over `reviews.createdAt` (both 120s). A pre-existing `rollupSeverities` helper in `modules/pulls/status.ts` (lowercase keys) was built for a counts-only variant — currently unused by the route. Evidence: `server/src/modules/pulls/routes.ts`.

## Tool & Library Notes

- **2026-08-27** — `server/src/app.ts` skips registering `@fastify/rate-limit` entirely when `config.nodeEnv === 'test'` ("Disabled under test so integration suites can hammer endpoints via inject()") — so a route's per-route `config: { rateLimit: {...} }` is completely INERT under the normal `*.it.test.ts` setup (`loadConfig({..., NODE_ENV: 'test'})`); calling a rate-limited route any number of times never returns 429. To actually assert a 429 (e.g. AC-43 on `POST /eval/run-all`, T7), build that one test's own `app` with `loadConfig({..., NODE_ENV: 'production', LOG_LEVEL: 'silent'})` instead — `nodeEnv` only gates two things in `app.ts`/`config.ts` (pretty-printed dev logs, and this rate-limit registration), so overriding it doesn't otherwise change behavior against a Testcontainer DB. Evidence: `server/src/app.ts:93-97`, `server/test/evals-dashboard.it.test.ts` ("POST /eval/run-all is rate-limited").
- **2026-08-08** — `GET /pulls/:id/smart-diff` declares only a `params` schema, and the client's `useSmartDiff` calls `api.get<SmartDiff>()` (a bare cast, no parse). So the Zod contract is compile-time only on this path: a `.default([])` on a new response field NEVER executes at runtime, and a React-Query cache entry written before the field existed still reaches components as `undefined`. Add the response schema, or write the consumer defensively (`file.findings ?? []`) — don't trust the default. Evidence: `server/src/modules/smart-diff/routes.ts:26-28`, `client/src/lib/hooks/smart-diff.ts`.
- **2026-06-14** — New DB columns: edit `db/schema/*.ts`, then `npm run db:generate` (drizzle-kit) auto-generates `00NN_*.sql` (e.g. `0010_solid_baron_zemo.sql` = `ALTER TABLE … ADD COLUMN`). Never hand-write migration SQL; apply with `npm run db:migrate`.
- **2026-08-18** — Passing a Zod schema with a `.default(...)` field (e.g. `BriefRisk.endpoint_refs`) as the `schema` in `LLMProvider.completeStructured<T>({ schema: z.ZodType<T>, ... })` fails to typecheck even when `T` is explicitly supplied: `z.ZodType<T>` defaults its `Input` generic param to `T` too, but a schema with `.default()` has `Input !== Output` (the field is optional on input, required on output), so TS flags the object literal as non-assignable. Fixed with a narrow `schema: BriefSchema as unknown as z.ZodType<T>` cast — safe because only the Output side matters at the call site and `completeStructured` never re-serializes against `Input`.
