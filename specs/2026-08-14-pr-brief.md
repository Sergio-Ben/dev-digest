# Spec: PR Brief   |   Spec ID: SPEC-2026-08-14-pr-brief   |   Status: draft
Supersedes: none

## Problem & why

A reviewer opening a PR in DevDigest today gets three disconnected surfaces on the Overview
tab: the Intent card (`IntentCard.tsx` — what the PR claims to do), the Blast Radius card
(`BlastRadiusCard.tsx` — what it structurally touches), and, only after a review run, a
verdict banner with a flat findings list. Nothing answers the question a reviewer actually
asks first: **"What am I looking at, how dangerous is it, and which four lines do I read
before anything else?"**

The reviewer has to synthesise that themselves — cross-referencing scope against a caller
tree against a findings list. That synthesis is the expensive part of a review, it is done
badly under time pressure, and it is redone by every reviewer on the PR.

The PR Brief closes that gap: one card at the top of the Overview tab that states what the
PR changes and why, assigns a risk level, lists concrete risks anchored to real files, and
ranks a short **review focus** list — the specific file:line locations to read first.

Two pieces of the substrate already exist and are unused: the `pr_brief` table
(`server/src/db/schema/reviews.ts:57` — `pr_id` PK + `json` jsonb) and the `risk_brief`
feature-model slot (`server/src/vendor/shared/contracts/platform.ts:58`). This spec fills
them in.

The cost constraint is the same one the Intent Layer established: **no diff hunk bodies are
sent to the model.** The brief is assembled from already-computed, already-paid-for signals
(intent, blast radius, diff stats, linked issue, referenced specs) plus file paths and `@@`
hunk headers. The brief is a *composition* step, not a second read of the diff.

## Goals / Non-goals

### Goals

- G1: One structured LLM call composes a `Brief` from signals that already exist, so the
  marginal cost of the brief is a single cheap call over a few KB of metadata.
- G2: Every file, line, and endpoint the brief cites is **verifiably real** — present in the
  PR's changed-file set or in the blast radius facts. Anything else is dropped before the
  brief is stored, following the same discard-don't-repair posture as
  `reviewer-core/specs/grounding-spec.md`.
- G3: The brief is cached against a specific PR state and is not silently reused after the PR
  changes underneath it.
- G4: A reviewer can jump from a review-focus row straight to that file and line in the
  Files-changed tab, in one click.
- G5: The brief degrades rather than fails: a missing clone, an unindexed repo, a degraded
  blast radius, or an absent linked issue each remove a section of input, not the feature.

### Non-goals

- N1: **Not** a second review pass. The brief does not read change bodies, does not produce
  findings, and does not write to `findings`. Findings remain the review pipeline's output.
- N2: **Not** a replacement for the Intent card or the Blast Radius card. Those surfaces stay;
  the brief sits above them and cites them.
- N3: **No repo-wide semantic spec retrieval** (embeddings / vector search). "Relevant specs"
  in v1 means the specs and plans already referenced from the PR body, resolved by the
  existing `intent/references.ts` resolver. See Open questions Q2.
- N4: No PR-level numeric score. The screenshot's `PR SCORE` badge is the existing review
  score and is out of scope here; the brief contributes a categorical `risk_level` only.
- N5: No new MCP tool in v1 (`devdigest_get_brief`). See Open questions Q4.
- N6: No automatic brief computation on PR ingest/polling. The brief is computed on demand
  (Overview open, or explicit regenerate).

## User stories

- **US-1 — Triage.** As a reviewer opening PR #482, I want a one-paragraph statement of what
  changes and why plus a risk level, so I can decide within ten seconds whether this needs my
  full attention now or can wait.
- **US-2 — Read order.** As a reviewer, I want a ranked list of file:line locations to read
  first, so I spend my attention on the two lines that can hurt production rather than the
  ninety lines of lockfile churn.
- **US-3 — Trust.** As a reviewer, I want every risk to point at a file path I can click and
  verify, so I can tell an actual risk from a plausible-sounding sentence.
- **US-4 — Freshness.** As a reviewer returning to a PR that got three new commits, I want the
  brief to reflect the current head, not the state from yesterday.
- **US-5 — Control.** As a reviewer who thinks the brief missed the point (or who just fixed
  the flagged issue), I want a Regenerate button that recomposes it from current signals.
- **US-6 — Cost visibility.** As the workspace owner, I want the brief to reuse cached intent
  and blast results rather than recomputing them, and I want its model choice to be the
  `risk_brief` slot I already control in Settings.

## Acceptance criteria (EARS)

### Input assembly

- AC-1: WHEN a brief is composed for a PR, the system **shall** assemble its model input from
  exactly these sources: (a) PR title, body, author, branch, base; (b) diff stats — additions,
  deletions, changed-file count; (c) the ordered list of changed file paths; (d) the `@@` hunk
  headers for each changed file; (e) the PR's Intent record; (f) the PR's blast radius result
  including its summary sentence; (g) the linked issue title + body when one resolves;
  (h) the resolved referenced specs/plans.
  _(observable: a fixture PR yields a prompt containing all present sections and no others)_
- AC-2: The system **shall not** include any diff hunk **body** line (added, removed, or
  context) in the model input — only file paths and reconstructed `@@ -a,b +c,d @@` headers,
  as `intent/classifier.ts` already does.
  _(observable: for a fixture diff, no `+`/`-`/context source line from the diff appears
  anywhere in the assembled prompt string)_
- AC-3: The system **shall** obtain the Intent by calling the existing intent service's
  cached-or-compute path, so a PR that already has a stored intent costs zero additional LLM
  calls for that input.
  _(observable: composing a brief for a PR with a stored intent issues no intent-model call)_
- AC-4: The system **shall** obtain the blast radius by calling the existing blast service for
  the PR, and **shall** pass its facts (changed symbols, caller rows, impacted endpoints,
  affected crons, prior overlapping PRs) plus its summary sentence into the input.
  _(observable: the assembled prompt contains the blast summary sentence and the endpoint list
  returned by the blast service)_
- AC-5: IF the blast radius comes back degraded (any `degraded: true` reason — flag off, index
  failed, index partial, repo too large, no data), THEN the system **shall** compose the brief
  from the remaining inputs and **shall** record that the blast section was unavailable, rather
  than failing the request.
  _(observable: a PR in an unindexed repo still returns a complete `Brief`, and the stored
  record marks blast as degraded)_
- AC-6: The system **shall** resolve the linked issue and referenced specs/plans using the
  existing PR-body reference parser and resolver, and **shall** treat every failure to resolve
  (no PAT, no clone, 404, fetch disabled) as "that section is absent", never as an error.
  _(observable: a PR whose body links a nonexistent issue still composes a brief; the section
  is simply missing from the prompt)_
- AC-7: The total size of resolved reference content included in the input **shall** be bounded
  by a single named constant, and content beyond that bound **shall** be truncated with an
  explicit truncation marker rather than dropped silently.
  _(observable: a PR referencing a 200 KB spec produces an input at or under the bound,
  containing a visible truncation marker)_
- AC-8: WHERE a section of input is absent, the system **shall** omit that section's heading
  entirely rather than emitting an empty heading.
  _(observable: a PR with no body and no references produces a prompt with no
  "PR Description" or "Referenced plans/specs" headings)_
- AC-9: The system **shall** derive the set of **citable files** as the PR's changed-file paths,
  and the set of **citable endpoints** as the blast radius's impacted endpoints plus affected
  crons, and **shall** carry both sets forward to the grounding step (AC-15..AC-20).
  _(observable: both sets are computed from the same inputs given to the model, verified by test)_

### Model call & output contract

- AC-10: The system **shall** produce the brief with **exactly one** structured model call per
  composition, using the shared structured-completion port and a `Brief` schema.
  _(observable: a single composition issues exactly one brief-model call; counted in a test double)_
- AC-11: The model **shall** be resolved from the existing `risk_brief` feature-model slot, so a
  workspace override in Settings takes effect without a code change.
  _(observable: overriding `risk_brief` in Settings changes the provider/model used for the next
  composition)_
- AC-12: The `Brief` returned **shall** carry: `what` (what the PR changes), `why` (why it
  changes it), `risk_level`, `risks[]`, and `review_focus[]`.
  _(observable: the schema rejects an object missing any of the five fields)_
- AC-13: Each entry in `risks[]` **shall** carry a kind, a title, an explanation, a severity, and
  at least one file reference; each entry in `review_focus[]` **shall** carry a file path, an
  optional line number, and a one-line reason stating what to check there.
  _(observable: the schema rejects a risk with an empty file-reference list and a focus item with
  no reason)_
- AC-14: `review_focus[]` **shall** be ordered most-important-first and **shall** be capped at a
  single named maximum; entries beyond the cap **shall** be dropped, not merged.
  _(observable: a model returning 12 focus items yields exactly the cap, in the model's order)_

### Grounding — citations must be real

- AC-15: WHEN the model returns a risk whose file reference does not resolve to a path in the
  citable-file set (AC-9), THEN the system **shall** drop that reference.
  _(observable: a risk citing `src/does-not-exist.ts` loses that reference)_
- AC-16: IF dropping references under AC-15 leaves a risk with zero references, THEN the system
  **shall** drop the entire risk.
  _(observable: a fully hallucinated risk does not appear in the stored brief)_
- AC-17: A file reference of the form `path:line` **shall** be accepted when `path` is in the
  citable-file set, and the line number **shall** be preserved for deep-linking; a bare `path`
  **shall** be accepted with no line.
  _(observable: `src/config.ts:12` survives with line 12; `src/config.ts` survives with no line)_
- AC-18: WHEN a `review_focus[]` entry names a file outside the citable-file set, THEN the system
  **shall** drop that entry.
  _(observable: a focus row pointing at an unchanged file does not appear in the stored brief)_
- AC-19: WHERE a risk or focus entry cites an endpoint or cron, that citation **shall** be
  dropped unless it appears in the citable-endpoint set (AC-9).
  _(observable: an invented `GET /api/admin` citation is removed while a real impacted endpoint
  survives)_
- AC-20: AFTER grounding, IF the surviving risks' highest severity is lower than the model's
  returned `risk_level`, THEN the system **shall** downgrade `risk_level` to that highest
  surviving severity; IF no risks survive, THEN `risk_level` **shall** be the lowest level and
  `risks[]` **shall** be empty.
  _(observable: a brief whose only `high` risk was hallucinated is stored with a downgraded
  `risk_level`, mirroring the score recomputation in the grounding spec)_

### Caching & regeneration

- AC-21: WHEN a brief is composed, the system **shall** persist it in the existing `pr_brief`
  row for that PR, together with the PR state it was composed for and the provider/model used.
  _(observable: after composition, the `pr_brief` row contains the brief plus its state key)_
- AC-22: The persisted state key **shall** be derived from the PR's head SHA **and** a
  fingerprint of the composed inputs (at minimum: the intent record and the blast radius facts),
  so that recomputing the intent invalidates the brief.
  _(observable: recomputing intent for a PR, then requesting the brief, yields a fresh
  composition rather than the cached one)_
- AC-23: WHEN a brief is requested and a stored brief's state key matches the PR's current state,
  the system **shall** return the stored brief and **shall not** issue any model call.
  _(observable: a second request for an unchanged PR issues zero model calls)_
- AC-24: WHEN a brief is requested and the stored brief's state key does not match (new head SHA,
  recomputed intent, or changed blast facts), the system **shall** recompose and overwrite the
  stored brief.
  _(observable: pushing a commit and reopening the PR yields a brief marked for the new head SHA)_
- AC-25: WHEN regeneration is explicitly requested, the system **shall** recompose and overwrite
  the stored brief even if the state key matches.
  _(observable: pressing Regenerate on an unchanged PR issues exactly one new brief-model call)_
- AC-26: The persisted record **shall** carry a schema version, and a stored record whose schema
  version is not the current one **shall** be treated as a cache miss rather than deserialised.
  _(observable: a row written under an older version triggers recomposition, no deserialisation error)_
- AC-27: WHERE two brief requests for the same PR overlap, the system **shall** ensure at most one
  composition is in flight for that PR; the second request **shall** await the first's result
  rather than issuing a second model call.
  _(observable: two concurrent requests produce one model call and two identical responses)_

### API surface

- AC-28: The system **shall** expose `POST /pulls/:id/brief`, which assembles the inputs, returns
  the cached brief when the state key matches, and composes a fresh one otherwise.
  _(observable: the route returns a `Brief` payload for a valid PR id)_
- AC-29: `POST /pulls/:id/brief` **shall** accept an optional force flag that bypasses the cache
  and forces recomposition (AC-25).
  _(observable: the same route with the flag set recomposes an unchanged PR)_
- AC-30: The system **shall** expose `GET /pulls/:id/brief`, which returns the stored brief when
  its state key matches and otherwise composes one, mirroring the intent module's
  lazy-compute-on-read behaviour, so the card can load without a mutation.
  _(observable: opening the Overview tab on a PR with no stored brief returns a composed brief
  from a GET)_
- AC-31: Both routes **shall** be workspace-scoped and **shall** return not-found for a PR id
  outside the caller's workspace, and the composing routes **shall** be rate-limited on the same
  basis as the other one-LLM-call routes.
  _(observable: a cross-workspace id returns not-found; exceeding the limit returns a rate-limit
  response)_
- AC-32: IF the brief model call fails, THEN the route **shall** return an error response and
  **shall not** overwrite a previously stored, still-valid brief.
  _(observable: forcing a provider error leaves the prior stored brief intact and readable)_

### UI — `PrBriefCard`

- AC-33: The PR Overview tab **shall** render a `PrBriefCard` above the Intent / Blast Radius
  pair, under a "PR Brief" section label.
  _(observable: the card appears first in the Overview tab's DOM order)_
- AC-34: The card **shall** display the `risk_level` as a visually distinct level indicator whose
  meaning is conveyed by text as well as colour.
  _(observable: the level is readable with colour removed; the level's text label is in the
  accessible name)_
- AC-35: The card **shall** display `what` and `why` as prose, and `risks[]` as a list where each
  row shows the risk title and its file reference(s).
  _(observable: a brief with three risks renders three rows, each showing at least one path)_
- AC-36: The card **shall** display `review_focus[]` as an ordered list under a "Review focus —
  read these first" heading, each row showing the file (with line when present) and the reason.
  _(observable: focus rows render in stored order with path, line, and reason)_
- AC-37: WHEN a review-focus row is activated, the system **shall** navigate to that file (and
  line, when present) in the Files-changed tab, reusing the Overview tab's existing
  open-file-at-line affordance.
  _(observable: activating a focus row switches tabs and scrolls the diff to that file and line)_
- AC-38: Review-focus rows and risk file references **shall** be operable by keyboard and expose
  an accessible name that includes the file path.
  _(observable: each row is reachable by Tab and activatable by Enter/Space)_
- AC-39: The card **shall** expose a Regenerate control that triggers AC-25, shows a pending
  state while in flight, and is disabled while pending.
  _(observable: pressing Regenerate disables the control and shows a loading state until the new
  brief arrives)_
- AC-40: The card **shall** render a loading state while the brief is being fetched or composed,
  and an error state with a retry affordance when the request fails.
  _(observable: the three states render distinctly for loading / error / loaded)_
- AC-41: WHERE the brief cannot be composed because the PR has no changed files, the card
  **shall** render the existing unavailable message and hint rather than an empty card.
  _(observable: a PR with zero changed files renders the unavailable state)_
- AC-42: All card copy **shall** come from the `brief` message namespace; the card **shall not**
  contain hard-coded user-facing English.
  _(observable: no literal user-facing string appears in the component source)_

### Observability

- AC-43: Each composition **shall** log which input sections were present, which were absent and
  why, and the resolved provider/model — so a thin brief can be diagnosed from logs without
  rerunning it.
  _(observable: the log line for a composition names the present/absent sections)_
- AC-44: Each composition **shall** log the count of risks and focus entries the model returned
  versus the count that survived grounding.
  _(observable: a composition with two dropped risks logs the before/after counts)_
- AC-45: Each composition **shall** log the estimated token size of the assembled input and the
  estimated size a full-diff input would have been, using the same estimation method the intent
  classifier uses, so the savings claim is measurable rather than asserted.
  _(observable: the log line carries both estimates for a fixture PR)_

### Untrusted handling (security)

- AC-46: PR title, PR body, linked issue content, and resolved spec/plan content **shall** be
  wrapped as untrusted content before inclusion in the prompt, using the existing wrapper.
  _(observable: every such section in the assembled prompt is enclosed in an untrusted block)_
- AC-47: A PR body or spec containing prompt-injection text **shall** be treated as data: the
  composition **shall** still produce a schema-valid `Brief`, and any file or endpoint the
  injected text tries to introduce **shall** be removed by grounding (AC-15..AC-19) unless it is
  genuinely in the citable sets.
  _(observable: a fixture PR body instructing the model to cite `/etc/passwd` yields a brief with
  no such citation)_
- AC-48: The composition **shall not** read any file outside the repo clone, and **shall not**
  follow external URLs when external fetching is disabled.
  _(observable: a crafted `../../` reference is refused; with fetching disabled, no outbound
  request is made)_

### Headline scenario

- AC-49: GIVEN PR #482 "Add rate limiting to public API endpoints" with 9 changed files, a stored
  intent, and an indexed repo, WHEN the reviewer opens the Overview tab, THEN the card **shall**
  render within one composition: a risk level, a what/why paragraph, risks anchored to real
  changed files (e.g. an auth-surface risk on the rate-limit middleware and a new-dependency risk
  on `package.json`), and a review-focus list whose top rows are real `file:line` locations —
  and clicking the top row **shall** open that file at that line in the Files-changed tab.
  _(observable: end-to-end on a seeded fixture PR, one brief-model call, all cited paths present
  in the PR's changed-file set)_

## Edge cases

- PR with zero changed files (empty diff, or files not yet synced) → no citable files, so nothing
  could be grounded; the card renders the unavailable state and no model call is made. → AC-41, AC-9.
- Repo not cloned / repo-intel index missing → blast degraded; brief composes from intent + diff
  stats + paths alone, and review focus is limited to changed files. → AC-5.
- Intent absent and intent computation fails → the brief composes without the intent section
  rather than failing, and logs the absence. → AC-6, AC-8, AC-43.
- Model returns a well-formed brief where **every** citation is hallucinated → all risks and focus
  entries drop; the stored brief has empty lists and the lowest risk level; the card shows the
  "no notable risks" copy rather than an empty region. → AC-16, AC-18, AC-20, AC-35.
- Model returns `risk_level: high` with only `low`-severity surviving risks → downgraded to `low`.
  → AC-20.
- Model cites a real file with a line number beyond that file's length → **accepted in v1**: the
  path is real, so the citation survives and the diff viewer clamps to the nearest available
  anchor. Line numbers are not validated against file length. See Open questions Q3.
- Model cites a file that is changed but whose citation is a directory (`src/api/`) → not an exact
  path match, so it is dropped. → AC-15.
- Duplicate review-focus entries for the same file:line → **accepted: deduped by `file:line`,
  first occurrence wins**, consistent with the reference dedupe in the intent module.
- New commit lands between the GET that composed the brief and the user reading it → the brief is
  shown as composed; the next request detects the SHA change and recomposes. There is no live
  invalidation push. → AC-22, AC-24.
- Intent recomputed from the Intent card while a brief is displayed → the displayed brief is now
  stale; the next brief request recomposes. The client **should** invalidate its brief query when
  intent recompute succeeds. → AC-22.
- Two reviewers press Regenerate simultaneously → single-flight; one composition, both see the
  same result. → AC-27.
- Provider outage during regeneration → error state with retry; the previously stored brief is not
  destroyed and is still what a subsequent successful read returns. → AC-32, AC-40.
- Very large PR (hundreds of changed files) → the input is paths + hunk headers only, so it stays
  small; no cap on the file list in v1, and the token estimate log makes the volume visible.
  → AC-2, AC-45.
- Referenced spec far larger than the reference budget → truncated with a marker, not dropped, so
  the model sees the beginning of the document and knows it was cut. → AC-7.
- Stored brief written by an earlier schema version → treated as a miss and recomposed. → AC-26.
- PR is closed or merged → the brief still composes and is still readable; nothing about the brief
  is gated on PR status.

## Non-functional

- **Cost.** The brief's own model interaction is exactly one structured call over an input of
  metadata, paths, and hunk headers (AC-2, AC-10). Dependency calls are bounded: at most one
  intent call (only on intent cache miss) and at most one blast summary call. A warm PR — stored
  intent, unchanged head — costs zero calls (AC-23).
- **Latency.** A cache hit is a single row read and **should** render without a visible spinner.
  A cold composition is dominated by the one model call plus the blast radius read.
- **Determinism.** Grounding is a pure function of (model output, citable-file set,
  citable-endpoint set): same inputs → same surviving brief, no side effects. This mirrors the
  purity requirement on `groundFindings()`.
- **Degradation.** Every input source except the PR row itself is optional (AC-5, AC-6). Only a
  missing PR or a failed brief-model call produces an error response.
- **Accessibility.** Risk level is not conveyed by colour alone (AC-34); focus rows are keyboard
  operable with the path in the accessible name (AC-38).
- **i18n.** All copy lives in the `brief` message namespace, which already exists and already
  carries `unavailable`, `unavailableHint`, and `noRisks` (AC-42).

## Cross-module interactions

```
client
  PrBriefCard ──GET /pulls/:id/brief────────────┐
              └─POST /pulls/:id/brief (force) ──┤
                                                ▼
server: brief module (new)
  routes  ──► BriefService
                │
                ├─► IntentService.getOrCompute        (L03 — intent, cached)
                ├─► BlastService.getForPr(summary)    (L04 — blast, incl. summary)
                ├─► ReviewRepository: pull row, repo row, changed file paths, diff stats
                ├─► loadDiff → hunk headers only
                ├─► intent/references.ts: parseReferences + resolveReferences
                │        (linked issue, repo specs/plans)
                ├─► settings/feature-models: resolveFeatureModel('risk_brief')
                ├─► llm.completeStructured(Brief)      ← the one call
                ├─► grounding (pure): drop unreal citations, downgrade risk_level
                └─► persist to pr_brief (json + state key)
```

- **`intent` module** — consumed, not modified. The brief calls the existing cached-or-compute
  path and reuses `parseReferences` / `resolveReferences` for the linked issue and specs. This
  makes `intent/references.ts` a shared dependency of two modules; it is already a pure,
  injected-dependency helper, so no change is required to share it.
- **`blast` module** — consumed, not modified. The brief calls the existing per-PR blast read and
  uses both its facts and its summary sentence.
- **`reviews` module** — the brief reads the PR row, repo row, changed file paths, and diff via
  the existing review repository and diff loader. The brief does **not** participate in a review
  run and does not write findings (N1).
- **`settings` module** — the `risk_brief` slot already exists in the feature-model registry and
  is already surfaced in Settings; no registry change is needed.
- **Shared contracts** — `Brief`, `BriefRiskLevel`, and `ReviewFocusItem` are added to the
  existing brief contracts file. The existing `Risk` / `RiskSeverity` schemas there are reused
  as-is for `risks[]`.
- **Database** — no migration. The existing `pr_brief` table (`pr_id` PK + `json` jsonb) holds
  the record, and the state key, schema version, and model metadata live **inside** the json
  envelope. This is deliberate: `server/src/db/migrations/` is a do-not-touch path, and the
  envelope is sufficient for cache validation.
- **Module registration** — the new brief module is added to the static registry in
  `server/src/modules/index.ts`, per the project's no-autoload convention.

## Contracts

Added to the shared brief contracts (`contracts/brief.ts`), reusing what is already there:

- **`BriefRiskLevel`** — the PR-level risk classification. Reuses the value set of the existing
  `RiskSeverity` (`high` | `medium` | `low`) so that AC-20's comparison between a risk's severity
  and the PR's level is a comparison over one ordered domain, not two.
- **`ReviewFocusItem`** — `{ file, line (nullable), reason }`, optionally carrying an endpoint or
  cron citation. `file` is a repo-relative path from the citable-file set; `line` is the anchor
  used by AC-37's deep link; `reason` is the one-line "what to check here".
- **`Brief`** — `{ what, why, risk_level, risks, review_focus }` where `risks` is an array of the
  existing `Risk` schema and `review_focus` is an array of `ReviewFocusItem`. This is the shape
  the model is constrained to and the shape the HTTP routes return.
- **Stored envelope** — the `pr_brief.json` value is `{ schema_version, state_key, head_sha,
  generated_at, provider, model, degraded_inputs, brief }`. Only `brief` is returned to the
  client by default; the envelope exists to serve AC-21, AC-22, AC-26 and to make a stale or
  thin brief explainable after the fact.

**Naming note.** A `PrBrief` schema already exists in `contracts/brief.ts` as
`{ intent, blast, risks, history }` — a Part-0 placeholder for a composite `pr_brief.json`
artefact. It is never constructed or consumed: its only appearance outside the contracts file is a
type re-export in the client's type barrel (`client/src/lib/types.ts:35`). This spec introduces `Brief` as a
**distinct, narrower** contract and leaves `PrBrief` untouched. Retiring the placeholder is
deliberately deferred. See Open questions Q1.

## Untrusted inputs

Every input that originates outside the operator's control is untrusted and is wrapped before it
reaches the model (AC-46):

| Input | Origin | Treatment |
|---|---|---|
| PR title, PR body | PR author | wrapped untrusted |
| Linked issue title/body | issue author | wrapped untrusted |
| Referenced specs/plans | repo contents | wrapped untrusted, size-bounded (AC-7) |
| External URL content | the internet | only when external fetching is enabled (AC-48), wrapped untrusted |
| Changed file paths, hunk headers | the diff | structural, not prose — but still author-controlled, and used **only** as the citable-file allowlist |
| Intent, blast summary | our own models | model output; not privileged, still passes through grounding |

The structural defence is grounding, not prompt wording: the model can be talked into *saying*
anything, but it cannot make a path exist in the citable-file set. A citation is kept because it
matches a set computed from the diff, never because the model asserted it (AC-15..AC-19). This is
the same discard-don't-repair posture the findings grounding gate takes.

## Open questions

- **Q1 — Retire the placeholder `PrBrief`?** The existing `PrBrief` schema
  (`{ intent, blast, risks, history }`) is a never-constructed placeholder. Options: leave it (this spec's
  assumption), fold it into `Brief` as a superset, or delete it in a follow-up. Deleting it is a
  shared-contract change and wants its own decision.
- **Q2 — Spec relevance beyond PR-body references.** v1 resolves only the specs and plans the PR
  body links (N3). A PR that touches `server/src/modules/blast/` arguably wants
  `server/specs/review-flow.md` in the input even if nobody linked it. Path-prefix matching against
  the project-context discovery result is the cheap next step; semantic retrieval is a separate
  feature. **Assumption for v1:** PR-body references only.
- **Q3 — Validate cited line numbers against file length?** v1 accepts any line number on a real
  path (see Edge cases). Validating would require reading the file from the clone, which the brief
  otherwise never does. **Assumption for v1:** path is validated, line is not.
- **Q4 — MCP exposure.** The MCP server already exposes blast radius, findings, and conventions.
  A `devdigest_get_brief` tool is a natural sibling and is deliberately out of v1 scope (N5).
- **Q5 — Should a completed review run invalidate the brief?** A run produces findings that would
  sharpen `review_focus`, but the brief deliberately does not read findings (N1). If findings
  should feed the brief, that is a scope change: it adds a source to AC-1 and a trigger to AC-22.
  **Assumption for v1:** review runs do not invalidate or feed the brief.
- **Q6 — Regeneration rate limit.** AC-31 defers to "the same basis as other one-LLM-call routes"
  (the intent recompute route uses a modest per-minute limit). Confirm that limit is right for a
  button a reviewer may press repeatedly while iterating.
